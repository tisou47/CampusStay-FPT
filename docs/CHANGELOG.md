| ADR-16 | 20/10/2026 | Deployment: the web app on **Vercel** (Hobby, Git integration, a preview per pull request); the API and PostgreSQL 17 on one **Ubuntu VPS** (x86-64, 2 vCPU / 4 GB recommended, any provider) with Docker Compose and Caddy (Let's Encrypt HTTPS). CORS takes origin patterns so Vercel previews can call the API. *Revised 22/10/2026:* the Oracle Cloud Always Free VM first chosen was dropped because sign-up failed at the card check. Target: an **Azure for Students** VM (B2ats v2 or B2pts v2 in the free hours) with **Azure Database for PostgreSQL** Flexible B1ms (free for 12 months), or any VPS with Postgres in the stack (runbook appendix A). *Live 23/10/2026:* Azure VM `campusstay-vm` (East Asia, B2ats v2) + Azure Database for PostgreSQL (runbook appendix A, layout A); API `https://campusstay-api.eastasia.cloudapp.azure.com/api`, web `https://campusstay-fpt-ten.vercel.app` | A VPS never sleeps, so the 30-second email outbox job, the local `FileStorage` volume and Gmail SMTP work unchanged, and the SePay webhook gets a stable HTTPS URL (OI-07); a small plan costs a few dollars a month and a Vietnamese provider takes bank transfers. Vercel cannot host the long-running Spring Boot process; free PaaS tiers sleep, block SMTP or expire their database |
| ADR-17 | 22/10/2026 | Backend code in layered Spring MVC packages (`controller`, `service`, `repository`, `entity`, `dto`, `event`, `config`, `security`, `exception`, `common`; feature sub-packages inside the layers) instead of ten module packages; Spring Modulith removed, `LayeringTest` checks that calls go controller → service → repository | The standard layout is easier for the team and the council to follow than modules with hidden `internal`/`web` folders; classes moved without behaviour changes |
| ADR-18 | 24/10/2026 | The production server runs as a demo: `PAYMENT_SIMULATOR=true` (and `VITE_PAYMENT_SIMULATOR` on Vercel) enables the payment simulator (A-08) outside the dev profile, and `MAIL_REDIRECT_TO` sends every email to the team mailbox. | ADR-19 | 24/10/2026 | Managers work for the whole dormitory (no Block scope); Staff stay scoped to their Blocks; Managers review Applications, run and commit the assignment, confirm payments and issue next-Term fees; room changes and swaps inside one Block are decided by its Staff, across Blocks by a Manager (spec D-09, D-10, §3) | The dormitory has several Managers with the same responsibilities across Blocks; Block-level work (desk, rooms, maintenance, utility) belongs to the Staff |
| ADR-20 | 24/10/2026 | Registration periods: a Manager requests a Term with dates, rooms and prices; the Admin builds it in a wizard with prices per Term, Rooms and places, rules and house rules; publishing and every later money or policy change create announcements on the students' board (spec D-08, D-10, D-11, D-25). *Built 26/10/2026 (phase 4, in `main` and production since 26/10/2026):* one open request per Term, answered In progress, Needs changes or Rejected, Done when its Term is published; the wizard saves a Draft after each step and asks a reason for every value that differs from the request; publishing fixes the Term's price table, Deposit, Utility Deposit, eligibility switches, priority-group order and matching snapshot, which every reader then asks the Term for; afterwards a passed date is fixed, an open deadline only moves later and money locks with the first Invoice; Blocks used and Rooms left out bind the assignment and Round 2; renewal milestones are stored, optional until phase 6 uses them; Room Classes per Room stay Manager work (Room Classes by Term) | Managers decide the business values, the Admin the configuration; prices fixed per Term stop default-price edits from changing a running Term; students see every change |
| ADR-21 | 24/10/2026 | Stay length (1–9 Terms) on the Application; continuing residents keep their Bed into the next Term; a requests window (room change, swap, Room Class change with every continuing resident's consent, extension, end of stay) is decided before the next-Term fees; changes take effect next Term without price differences; enrollment reconciliation each Term. Amends ADR-12 (spec D-03, D-04, D-13…D-15, D-28…D-31). *Built 26/10/2026 (phase 6, in `main` and production since 27/10/2026):* a Stay counts the Terms committed and used; at M2 every resident not leaving keeps the Bed as a next-Term Allocation (Continuing, or Awaiting extension in the last Term, released at M3 without an extension); room changes, swaps, Room Class changes (every continuing resident agrees, the furniture is checked and reserved) and extensions are decided by M4, also in bulk, and only move next-Term Allocations; Managers reconcile the enrolled list (not enrolled → the next-Term Bed released, the Application rejected or the stay terminated) before issuing one next-Term fee per continuing resident at M6 (100 % of the next Term's price of the Bed held then; unpaid at M7 the Bed is released); a moved Allocation takes its Invoices along, a cancelled one voids or refunds its fee once; operational moves by Staff or Managers cost nothing; the turnover lists leavers, movers and Rooms needing a meter reading and a new code | Real dormitories renew residents; billing the next Term on the next Bed removes prorated charges and credits and their loopholes |
| ADR-22 | 24/10/2026 | Payments: the student claims "I have transferred", which stops the deadline; Managers confirm in bulk or reject. SePay, the bank-feed inbox and the payment simulator are removed. Supersedes ADR-08 and the simulator part of ADR-18 (spec D-12). *Built 26/10/2026 (phase 5, in `main` and production since 26/10/2026):* a claim keeps the time left to the deadline and stops it (Deposit expiry, forfeit, reminders, Utility rules skip it); Managers confirm in bulk or one Invoice with a receipt (also a transfer not claimed yet), each paid at the time of its claim with its own audit entry; a rejection gives the time back (at least 12 h) and the second one cancels a Deposit or Balance, never a debt (Utility, charges); Managers get one summary per hour; an Invoice's money never changes once issued and a Paid or Void Invoice never comes back (database trigger), an Invoice is refunded once; the SePay inbox is kept read-only as an archive; the VietQR image is shown only when a receiving account is configured | No bank account or merchant contract exists; one manual path is simpler to demo, test and explain than three |
| ADR-23 | 24/10/2026 | Door codes: one 6-digit code per Room set by the Block's Staff, released to a resident once paid, from the check-in start and after it is confirmed on the lock; rotated whenever someone leaves; stored encrypted, every view audited. Paying the Balance makes a student a resident; an unpaid Balance forfeits the Deposit and the Bed unless an approved late check-in runs (spec D-18…D-20). *Built 25/10/2026 (phase 3):* codes AES-256-GCM with `DOOR_CODE_KEY`, proposed → confirmed on the lock → retired; check-out and moves to another Room open a rotation task for the Block's Staff; until phase 5 releases codes on payment, a student sees the code of the Room they are checked in to *Phase 5 (26/10/2026, in `main` and production):* the release (Balance paid, check-in start, code confirmed with no change waiting) runs after a payment, after a confirmed code and every 15 minutes; residence starts with the release, or with a desk check-in when the Room has no code, and Utility counts from then; the room map shows unpaid, paid (waiting for the code) and resident Beds; an unpaid Balance past its deadline is forfeited (Deposit kept by "Balance not paid", 0 % by default) unless a claim waits or an approved late check-in runs; late check-ins are also asked online and an approval moves the Balance deadline; terminations (Utility debt after the final warning, not enrolled, Manager) end with the check-out or rotate the code once overdue | The code is the real key to the Room; releasing and rotating it is what stops people staying without paying |

| ADR-28 | 29/10/2026 | Students' AI assistant (the *Could* "AI feature"): a chat on the student pages answered by a **self-hosted** open model on Ollama (default `qwen2.5:7b`), behind the adapter `AssistantModel`. The model never reads the database: its knowledge is a user guide (`assistant/guide_<vi\|en>.md`) and **the student's own data, read again for every question through the services of the student screens** and put in its instructions, so it sees only what the signed-in student sees (no door codes, no other student). Questions about the door code get a fixed answer without the model. 30/10/2026, after testing on the demo data: tool calling was dropped (a small model did not call tools reliably and made up answers) and the default model moved from `qwen2.5:3b` to `qwen2.5:7b` (the 3B model misread rows of similar data such as the price table). Built on `feat/ai-assistant`, web first, Android later (user decisions 29/10/2026, contract A-68) | The team chose a self-hosted model over a hosted API; the 1 GB production VM cannot run one, so the model server runs elsewhere (a developer machine with a GPU, reached through an authenticated tunnel) and the API degrades to "offline" when it is down. | ADR-29 | 10/11/2026 | Family Day (option A: visits in a common area). A Manager organises a Family Day for one Block; its residents register guests (name, relationship and year of birth only: no identity number, no account) for one time slot; within the slot's places the registration is **approved at once** and each guest gets their own pass (QR: a random token checked by the server). The Block's Staff check each guest in once (identity paper checked, inside the slot) and out; guests never enter the Rooms or stay overnight; the four roles stay. Defaults chosen with the user until the mentor confirms them: one registration and one slot per student, no re-entry, a guest under `family_day.adult_age` (18) comes with an adult, check-in from `family_day.early_minutes` (15) before the slot, a visit the guest did not end at the desk is closed by Staff with a note at the time they close it, a Family Day with guests already in is closed, not cancelled.
